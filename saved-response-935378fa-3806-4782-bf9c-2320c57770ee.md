# Сохранённый ответ (id: 935378fa-3806-4782-bf9c-2320c57770ee)

## Ошибка «ошибка БД» при авторизации (IT Shop)

### Почему была «ошибка БД» при входе

Текст **«ошибка БД»** в ответе на `POST /api/auth/login` отдаётся, когда запрос **`GetUserByLogin`** падает **не** с «пользователь не найден», а с реальной SQL-ошибкой. Частый случай: **том PostgreSQL создан раньше**, чем в репозитории появилась миграция **`000002`** с колонкой **`password_hash`**. Скрипты из `docker-entrypoint-initdb.d` при **существующем** volume **не выполняются снова**, поэтому в таблице `users` нет `password_hash`, а sqlc-запрос всё равно делает `SELECT … password_hash` → PostgreSQL возвращает ошибку → в API это превращается в «ошибка БД».

### Что изменено в коде

1. **`internal/dbschema/ensure.go`** — при старте API выполняются идемпотентные правки (как минимум `password_hash`, `justification`, таблица `attachments` из `000002`), чтобы старые БД подтягивались без ручного `psql` и без удаления volume.

2. **`cmd/api/main.go`** — после подключения пула вызывается **`dbschema.Ensure`**.

3. **`handlers_auth.go`** — в лог API пишется **реальная ошибка** (`GetUserByLogin`, `ListRbacNamesForUser`, `GetUserByID`), чтобы при следующем сбое было видно точную причину в консоли контейнера / терминале.

### Что сделать у себя

Пересоберите и перезапустите API, чтобы подтянулся новый бинарник:

```bash
cd itshop/deploy
docker compose up -d --build api
```

После этого логин с демо-пользователями (`initiator` / `password` и т.д.) должен проходить, если строка **`DATABASE_URL`** указывает на ту же БД, что и у контейнера.

Если ошибка останется — посмотрите логи: **`docker logs itshop_api`** — там теперь будет строка вида `auth login GetUserByLogin: ...` с точным текстом от PostgreSQL (нет связи, неверная БД, и т.д.).
